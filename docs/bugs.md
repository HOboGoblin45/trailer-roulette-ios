| B1 | S2 | YouTube trailers played ~15s then auto-advanced to the next one | Root cause: pre-roll ad ends fire onStateChange ENDED(0) before the real trailer plays, and every path advanced on the raw event. Added ad-aware end detection (progress fast-path + resume-confirm) in `src/lib/endDetection.js` (web), `TrailerPlayer.swift` (iOS), and `landing-page/api/embed.js` (proxy). v3.1.0. | 2026-07-07 |
| B2 | S2 | Trailers still stopped and skipped to the next one at ~13s (B1 regression class) | Root cause: the native 12s watchdog required a PLAYING event, but several pre-roll ad variants keep the content player UNSTARTED while the ad runs — no PLAYING fires, so live trailers were skipped as "unplayable" at 12s + ~1s load. Watchdog is now liveness-based (dead page 12s / silent player 20s / 75s hard cap) fed by a 1s proxy heartbeat; end detection hardened in all three mirrors (dual confirm window 5s→1.2s, pinned-duration fast-path gate, epoch token against stale cross-load messages); web backstop timer no longer poisonable by ad durations (+45s ad headroom). Fixed the pre-existing WKUserContentController handler retain leak while in there. v3.2.0. **Superseded by B3 — this fix was correct but incomplete and unreachable.** | 2026-07-13 |
| B3 | S2 | Trailers STILL skipped a few seconds in (B2 not actually cured) | Root cause: three variants of one mistake — trusting `onStateChange` in a bug defined by `onStateChange` not firing. (a) The only liveness signal B2 added was the `hb` heartbeat, which pre-v3.2.0 builds ignore; every installed app (2.11.0 / 3.1.0) still cancels its 12s watchdog solely on a `stateChange:1`, so redeploying the proxy fixed nothing in the field. The proxy now synthesises a `stateChange:1` (`syn:true`) once playback demonstrably advances, and owns a 75s no-playback error cap in exchange. (b) A pending end was cancellable only by a state event, so an ad pod whose next item started silently produced a false ENDED — forward playback progress now cancels it in all three mirrors (0.25s progress epsilon keeps a real end from cancelling itself). (c) The pin accepted any pre-PLAYING duration, i.e. the AD's during exactly these variants; pinning is now `initialDelivery`-only, and confirmation plus the fast-path require a pin instead of treating "no pin" as a match. Also: the native 75s hard cap now requires playback to have been frozen 20s, so it can't dismiss a playing trailer. New `embedProxy.test.js` executes the real Edge Function script (16 tests); native logic compiled and run under Linux Swift. v3.2.1. | 2026-08-14 |
| B4 | S1 | **Trailers play to the end and stop on YouTube's replay screen — they never auto-advance.** The original product-defining bug, open since v1.x through B1-B3 and five releases | Root cause, proven live 2026-08-16 against real YouTube (browser A/B on the same page/port): the proxy page only ever sent the IFrame API's `{ event:'listening' }` message — which arms the player but never asks YouTube to REPORT its state. `onStateChange`/`onError` are delivered only after an explicit `addEventListener` command. Without it the state channel is silent for the whole clip (infoDelivery keeps streaming, so every liveness/end-detection timer believed the page healthy), and the `ENDED` every mirror waits on never arrives. B1-B3 all tuned consumers of that absent event. Fix: the proxy subscribes (`addEventListener('onStateChange'/'onError')` on load + one 2.5s retry if silent; subscription is player-level, survives trLoad), so real ENDED now reaches the existing ad-aware end detection; native playlist handoff (v3.4.0) disabled because the widget fires NO ENDED between playlist items (`-1→3→1`) so `playlistDidAdvance()` could never sync. v3.4.2. **Device confirmation pending (handoff P0/P1):** the fix is logic-tested + live-proven at the widget level, but the full chain (proxy → native → JS queue) has not yet run on a phone; if P1 fails on device, reopen and re-examine the native mirror. | 2026-08-16 |

## Severity rubric
- **S1 (block submission)** — crash on launch, data loss, App Review flag
- **S2 (block release)** — major feature broken on a common device
- **S3 (fix in v1.1)** — minor visual or non-blocking interaction issue
- **S4 (nice to have)** — polish, copy, edge case
